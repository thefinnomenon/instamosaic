# Production Architecture

## Current Repository Inventory

The repository is a TypeScript workspace with an app package and shared packages:

- `app/`: Next.js App Router user pages, admin dashboard, route handlers, Stripe webhooks, PrintShrimp integration, request validation, and Cloud Tasks dispatch.
- `packages/db/`: Prisma client singleton and compatibility helpers for jobs, analytics, generated assets, dispatches, emails, downloads, print orders, and marketing records.
- `packages/mosaic/`: sharp-based mosaic generation and export definitions.
- `packages/storage/`: Cloudflare R2-compatible object storage abstraction with a local object-store fallback for development.
- `packages/worker/`: Instagram source fetching, reveal video generation, email sending, one-job processing, CLI loop, and Cloud Run-style HTTP worker endpoint.
- `scripts/`: local verification harnesses and marketing draft utilities.

The previous architecture used `better-sqlite3`, a SQLite database in `storage/`, generated files on local disk, and a long-running local worker loop. SQLite packages and runtime persistence have been removed. Local disk is now only scratch space for temporary generation files.

## Request Flow

1. The app validates an Instagram username, email, uploaded hero image, rate limits, and active-job constraints.
2. The hero image is written to temporary scratch space and uploaded to object storage under `jobs/<jobId>/inputs/`.
3. The app creates a `GenerationJob` row through Prisma.
4. The app creates a durable `JobDispatch` row and enqueues a Cloud Task containing only `{ "jobId": "<id>" }`.
5. Cloud Tasks invokes the private Cloud Run worker endpoint `POST /internal/jobs/process`.
6. The worker atomically claims an eligible queued job with a conditional Prisma update.
7. The worker loads authoritative job data from Postgres and downloads the hero input from object storage.
8. The existing Instagram download, mosaic generation, export, and reveal-video code runs in the worker, not in an app request.
9. Generated outputs are uploaded to object storage under deterministic job-scoped keys and recorded as `GeneratedAsset` rows.
10. The worker marks the job completed or failed in Postgres and sends idempotent completion or failure email through Resend.
11. Status pages and download endpoints read sanitized job state and asset records from Postgres. The browser never receives database credentials, Cloud Tasks credentials, worker auth secrets, or R2 privileged credentials.

## Persistence

Prisma models live in `prisma/schema.prisma`.

Important models:

- `GenerationJob`: status, progress, stage, attempt data, typed Instagram/payment fields, input metadata, completion/failure timestamps, and worker metadata.
- `GeneratedAsset`: one row per uploaded output variant, with bucket, object key, content type, size, dimensions, ETag, and timestamp.
- `JobDispatch`: durable dispatch/outbox records for Cloud Task enqueue attempts.
- `EmailDelivery`: unique `(jobId, kind)` delivery state for idempotent completion and failure emails.
- `AnalyticsEvent`, `LogEntry`, `Download`, `RateLimit`, `PrintOrder`, `MarketingTarget`, `MarketingPost`, and `InstagramMention`.

Prisma Postgres should use:

- `DATABASE_URL`: pooled runtime connection string for Vercel and Cloud Run.
- `DIRECT_URL`: direct connection string for migrations and administrative commands.

`prisma.config.ts` points migrations at `DIRECT_URL`, while the runtime singleton uses `DATABASE_URL` through `@prisma/adapter-pg`.

## Worker

The worker image is built from `Dockerfile` and starts:

```bash
npm run worker:http
```

Production endpoint:

```text
POST /internal/jobs/process
Content-Type: application/json

{ "jobId": "..." }
```

Cloud Run must not allow public unauthenticated invocation. Cloud Tasks should authenticate with an OIDC token using a service account allowed to invoke the Cloud Run service. Set Cloud Run concurrency to `1` initially because mosaic generation is CPU- and memory-intensive.

Development-only invocation is available with:

```env
CLOUD_TASKS_DEV_MODE=local
LOCAL_WORKER_URL=http://127.0.0.1:8080
WORKER_SHARED_SECRET=dev-worker-secret
```

The worker accepts `x-internal-worker-secret` when configured. `WORKER_ALLOW_UNAUTHENTICATED=true` is allowed only outside production.

## Object Storage

Configure Cloudflare R2-compatible storage:

```env
R2_BUCKET=instamosaic-production
R2_ACCOUNT_ID=...
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
R2_REGION=auto
```

Alternatively set `R2_ENDPOINT` directly. If R2 variables are absent, development stores objects under `tmp/object-storage` or `LOCAL_OBJECT_STORAGE_DIR`.

Generated bytes are not stored in Postgres. Postgres stores object metadata and job state only.

## Deployment Sequence

1. Create Prisma Postgres and set `DATABASE_URL` and `DIRECT_URL`.
2. Run `npm run prisma:generate`.
3. Run `npm run db:init` against the direct migration connection.
4. Create the R2 bucket and access key.
5. Build and deploy the worker image to Cloud Run as a private service.
6. Create a Cloud Tasks queue.
7. Grant the Cloud Tasks service account `roles/run.invoker` on the worker service.
8. Deploy the app to Vercel with the same Postgres/R2/Stripe/Resend settings and Cloud Tasks dispatch settings.
9. Configure Stripe webhooks to `POST /api/stripe/webhook`.
10. Submit a test generation and verify job progress, output asset rows, R2 objects, completion email, checkout, download, and print-order flow.

## Retry And Idempotency

- Cloud Tasks task names are deterministic per job, so duplicate enqueue attempts dedupe at Cloud Tasks.
- `JobDispatch` records preserve enqueue state for investigation and manual reconciliation.
- Worker claiming uses a conditional update on `GenerationJob.status = QUEUED`.
- Already completed jobs return without reprocessing.
- Output object keys are job-scoped and deterministic.
- `GeneratedAsset` uses unique `(jobId, type)` upserts.
- `EmailDelivery` uses unique `(jobId, kind)` claims to prevent duplicate completion and failure emails.

## Vercel App

The app package is a Next.js App Router app. Route handlers live in `app/src/app/api/**/route.ts` and delegate to the existing shared API handlers under `app/src/routes/api/**`.

Use these Vercel project settings:

```text
Framework preset: Next.js
Install command: npm install
Build command: npm --workspace app run build
Development command: npm run dev:app
```

Set production environment variables in Vercel project settings. Do not set local-only variables such as `CLOUD_TASKS_DEV_MODE`, `LOCAL_WORKER_URL`, or `WORKER_ALLOW_UNAUTHENTICATED` in production.
